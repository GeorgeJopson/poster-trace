# The scan redirect reads targets from a copy in Netlify Blobs, on a kept-warm function

This supersedes ADR-0019's decision that the redirect is an edge function, and its rejections of a standalone Node function and of a scheduled ping. Its other decisions stand: the redirect still handles scans itself, outside the layers, follows the stored target unchecked, serves the "poster not found" page with a `404`, and records scans in `context.waitUntil`.

After ADR-0019, the runtime started quickly, but the first scan after Neon had scaled to zero still waited from hundreds of milliseconds to seconds for its compute to start. Warming up the connection overlaps the TLS handshake but can't skip that. So `/redirect/{posterId}` (ADR-0014) is now served by `netlify/functions/redirect.mts`, a Node function in the site's functions region, which reads each poster's target from a copy in Netlify Blobs. Blobs has no cold state, so a read takes about the same time whether or not anything has run recently. The function only queries Neon for a poster that isn't in the copy. `netlify/functions/warm-up-redirect.mts` keeps it warm.

## Decisions

- **The database is the source of truth, and the copy is only a shortcut.** Each key is a poster id, and each value is its campaign's target as plain text. `ScanTargetCopy` (an application port, with `NetlifyScanTargetCopy` as its adapter) writes it after the database. `PosterService.generatePosters` writes the new posters' target. A failure there is logged, and the posters are still returned, because the redirect fills a missing copy itself. `CampaignService.updateCampaign` rewrites every poster of the campaign through `CampaignPosterLookup`. A failure there is thrown as `ScanTargetCopyError`, which the edit dialog shows. The changes are saved, but scans may still go to the old target, so the owner is asked to save again.
- **Every save rewrites the copy, even if the target didn't change.** Skipping a name-only edit would mean saving again could never repair a copy that an earlier failure left stale, because the database would already hold the new target.
- **On a miss, the redirect copies the target with `onlyIfNew`.** If the owner changed the target between the redirect's query and its write, the app has already copied the new target, and this older one mustn't overwrite it. A failed read of the copy also falls back to Neon.
- **A changed target takes up to 60 seconds to reach every scan.** The redirect reads the copy with eventual consistency (the default), so it's served from a nearby cache. The edit dialog tells the owner. A new key is readable straight away.
- **Production uses a site-wide store, and every other context uses a deploy store.** Production's store is `scan-targets-production` in `eu-central-1`, the Blobs region nearest the functions (London). A site-wide store defaults to `us-east-2` whatever the functions region, so the region is passed on every call. Otherwise a side that leaves it out silently sees an empty store. Deploy previews, branch deploys and `netlify dev` each have their own database branch, so they use `getDeployStore`, which starts empty and is filled by the fallback. A shared store would leak posters and target changes between them. The app and the function both open the store through `infrastructure/storage/scanTargetStore.ts`, so they can't drift apart. It has no path aliases and no `server-only`, so the function can bundle it.
- **The function queries Neon over HTTP with `@neondatabase/serverless`**, not through `@netlify/database`, which also loads `pg`, `ws` and two query builders, and so slows every cold start. Under `netlify dev`, whose Postgres Neon's HTTP driver can't reach, it imports `@netlify/database` instead. It connects on first use rather than at module load: Lambda freezes the process after each response, and work still running then can fail. It makes a new client when `NETLIFY_DB_URL` changes, as `@netlify/database` does.
- **A scheduled ping keeps one Lambda warm.** Every 5 minutes, on the production deploy only, `warm-up-redirect.mts` sends `X-Warm-Up: 1` to `/redirect/warm-up`. The redirect answers it with a `204` straight away. A ping touches neither Neon, because keeping it awake costs too much, nor Blobs, which has nothing to warm. Scans that arrive together can start a second, cold Lambda. That one pays for the Lambda starting, but not for Neon, which is accepted. If it becomes a problem, keep several warm. Previews aren't pinged.
- **A daily job deletes the copies of deleted posters.** `delete-orphaned-scan-targets.mts` runs `OrphanedScanTargetCleanup` on production. It lists the store's keys, checks them against `poster` in batches, and deletes the rest. There's no grace period, unlike ADR-0013's, because a copy is only written after its poster's row is committed. Until the job runs, a scan of a deleted account's poster redirects to its old target, not to the 404 page.

## Consequences

- **Saving a campaign's target scales with its posters.** It takes one Blobs write per poster, sent 20 at a time, within the save request. That's fine for hundreds of posters. If campaigns reach thousands, move to one key per campaign, with the poster-to-campaign mapping in the copy.
- **Two target edits saved at once can leave the copy out of step with the database.** If the owner saves two targets from two tabs, the database keeps the last save, while each poster's copy keeps whichever write finished last. Saving again fixes it. Only an owner racing themselves can cause it, so the copies aren't versioned.
- **Scans still wake Neon, after the redirect.** Recording a scan (ADR-0015) still inserts into Neon in `context.waitUntil`, so the scanner no longer waits for Neon, but the Lambda does.

## Considered Options

- **Putting the target in the QR code**, with an HMAC to stop an open redirect. It was rejected because the QR code would go from version 6 (41×41) to version 9–13 (53×53 to 69×69) at error correction `Q`. Changing a target would also no longer reach printed posters.
- **The Cache API, or a CDN-cached lookup endpoint.** They were rejected because both are cleared on deploy or per region, so the first scan of a rarely scanned poster would still wait for Neon.
- **Turning off Neon's scale-to-zero.** It was rejected because it costs money, and Netlify DB may not expose the setting.
